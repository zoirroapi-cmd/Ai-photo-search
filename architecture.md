# Архитектура AI Photo Search — план перехода к MVP

## Текущее состояние (прототип)
Всё в одном процессе на локальной машине:
- FastAPI + CLIP модель в памяти
- Эмбеддинги в файле `index.pt`
- Фото на локальном диске
- Без авторизации, один пользователь

## Целевая архитектура (MVP для демо)

### Компоненты

**1. Хранилище файлов — S3-совместимое объектное хранилище**
- Yandex Object Storage или Selectel (S3-совместимые, доступны из РФ)
- Структура: `users/{user_id}/photos/{file_id}.jpg`
- Сервер не хранит фото постоянно на диске

**2. База данных — Postgres + pgvector**
- Таблица `users` — пользователи
- Таблица `photos` — путь в S3, дата загрузки, EXIF дата съёмки, user_id
- Таблица `embeddings` (или колонка типа `vector` через pgvector) — CLIP-векторы, привязаны к photo_id
- pgvector делает быстрый поиск ближайших векторов прямо в SQL

**3. Очередь обработки — Redis + RQ (или Celery)**
- При загрузке фото: файл → S3, задача → очередь
- Воркер с GPU забирает задачу, считает CLIP-эмбеддинг, пишет в базу
- Пользователь видит "обрабатывается" пока не готово

**4. API — FastAPI (логика без модели)**
- Авторизация (JWT, либо Supabase Auth)
- Эндпоинты: загрузка фото, поиск, получение фото по id
- Сам текстовый запрос кодируется в API (это быстро), а не в воркере

**5. Face recognition — отдельный сервис/воркер**
- Та же логика что в `find_person.py`, но эмбеддинги лиц тоже в БД
- Привязка "образец лица" → "имя" хранится per-user

- Логика face_recognition — без изменений

а не САМ алгоритм поиска.
